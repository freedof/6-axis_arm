# 从 RRT-Connect 到视觉抓取闭环：让虚拟机械臂开始“看见并操作”

在上一篇阶段里，我把重点放在了 RRT-Connect 路径规划上：如何让机械臂从一个姿态运动到另一个姿态，同时避开障碍、满足关节限制，并尽量远离奇异区域。

完成这一步之后，机械臂已经不再只是做简单的关节插值，而是具备了真正的路径规划能力。但这还不等于“会抓东西”。

路径规划解决的是“怎么过去”的问题。抓取要解决的是另一组问题：

目标在哪里？
机械臂用什么执行器接触它？
相机怎样看到它？
大模型怎样理解图像？
深度信息怎样把图像里的目标变成三维位置？
规划结果怎样变成一次可验证的抓取动作？

所以，RRT-Connect 之后，项目的重心从“让机械臂会规划路径”，转向了“让机械臂具备感知和操作闭环”。

## 先把场景分开

RRT-Connect 阶段，我使用的是红蓝目标球场景。它很适合验证路径规划：目标明确，碰撞关系清楚，可以快速检查机械臂是否绕开障碍、是否能以指定姿态接触目标。

但抓取阶段不能继续混用这个场景。

抓取需要桌面、夹爪、动态物体、接触、摩擦、深度相机。红蓝小球场景服务于路径规划验证，方块抓取场景服务于操作闭环验证。两类场景如果混在一起，后续很容易出现测试污染：你以为自己在验证抓取，实际可能还被旧的目标球影响。

因此我做的第一件事，是把场景族分开。路径规划继续使用原来的红蓝目标球场景；抓取、相机和视觉识别则进入新的桌面方块场景。

这一步看起来只是工程整理，但对后续非常关键。机器人项目里，验证场景一旦混乱，后面每个结果都会变得含糊。

## 加入夹爪：从“末端点”到“末端执行器”

RRT-Connect 阶段，机械臂末端主要是一个参考点。它适合做运动学、IK 和路径规划，但它不能真正抓东西。

所以接下来我给机械臂加入了一个简化的两指平行夹爪。

一开始我也考虑过直接接入更真实的工业夹爪模型，比如 Robotiq 2F-85。但在这个阶段，我更关心的是先跑通闭环，而不是一上来追求高保真外观。复杂夹爪模型会带来更多坐标系、碰撞几何、接触参数和装配细节，容易让问题过早发散。

所以我选择先做一个可控的简化夹爪：

第一，它可以开合。
第二，它有碰撞体。
第三，它有高摩擦夹持面。
第四，它能在 MuJoCo 里和方块发生真实接触。

这个夹爪不是最终形态，但它足够支撑下一步：动力学抓取。

## 抓取不应该是“剧情触发”

如果没有动力学，抓取很容易被写成一种“剧情触发”：夹爪到了方块附近，方块就自动跟着夹爪走。

那不是抓取，只是动画。

我希望这个项目里的抓取至少满足一个基本要求：方块要因为接触和摩擦被夹起来，而不是因为代码把它绑定到了夹爪上。

于是我把桌面上的小方块设置成动态物体，让它具有质量、惯量、接触和摩擦。夹爪闭合时，两个手指通过高摩擦垫接触方块；随后机械臂抬升，如果接触关系稳定，方块会跟着被夹起来。

这一步让项目从“轨迹动画”进入了“物理交互”。

当然，这也带来了很多细节问题。

第一个问题是夹爪几何。早期版本里，手指结构偏长，摩擦垫偏短，看起来像是结构件在接触方块，而不是橡胶垫在夹持。后来我把结构手指缩短，并让摩擦垫与手指上下平齐，让真正的高摩擦区域成为主要接触面。

第二个问题是下降高度。夹爪如果下降太多，手指最低点会非常接近桌面，看起来像要顶到桌面，甚至可能出现穿刺风险。后来我把抓取姿态整体抬高，让夹爪夹住方块上半部，而不是让夹爪中心下降到方块中心附近。

第三个问题是速度。早期抓取 GIF 里，机械臂从高位下降到抓取点时有明显的“冲”和“过头”。后来我把轨迹速度按动作阶段拆开：先快速移动到方块上方，接近目标时单独放慢，夹住后再平稳抬升。

同时，仿真里不再只按 GIF 帧率更新关节目标，而是在每个物理仿真步重新采样连续轨迹。这样可以减少阶跃控制带来的抖动和过冲。

这些调整听起来很小，但它们决定了抓取结果是否“像一次真实动作”。

## 给机械臂装上第一视角相机

有了夹爪之后，下一步是让机械臂自己看见桌面。

我在夹爪根部加了一个简化版 D435i 深度相机。这个阶段没有直接导入真实相机外观模型，因为当前重点不是外观，而是 RGB-D 数据链路。

这个相机需要提供几类信息：

RGB 图像，用于视觉语言模型判断目标区域。
深度图，用于把图像区域变成三维位置。
相机内参，用于从像素坐标反投影。
相机外参，用于把相机坐标变换到世界坐标。
深度噪声，用于让仿真更接近真实传感器。

这一步让机械臂从“被外部观察”变成了“自己携带第一视角感知”。

后续所有视觉定位，都基于这个夹爪根部相机完成。

## 大模型负责“看图选区域”，不是直接控制机械臂

接入视觉语言模型时，我刻意做了一个边界划分：大模型只负责在 RGB 图上找目标区域，不直接输出机械臂关节角，也不直接给出最终抓取动作。

完整分工是：

视觉语言模型负责看图，输出目标区域。
深度相机负责提供该区域内的深度。
几何模块负责把二维图像区域反投影到三维世界坐标。
规划模块负责根据三维目标生成抓取姿态和路径。
MuJoCo 负责验证抓取过程中的接触和动力学。

这个分工很重要。

大模型擅长语义理解，比如“找到桌面上的红色小方块”。但它不应该绕过深度相机，也不应该直接决定机械臂怎么动。机械臂动作仍然要经过几何计算、碰撞检查、奇异性检查和路径规划。

换句话说，大模型是感知链路中的一个环节，而不是整个机器人控制系统。

## 从单视角到多视角

单视角识别很容易出问题。

目标可能很小。
阴影可能被误认为物体。
方块侧面可能导致框偏大。
视角太低时，桌面和目标边界不明显。
模型有时会框到背景或桌面。

为了解决这个问题，我加入了多视角拍照。相机从方块上方和几个斜上方位置观察同一个目标。这样做有两个好处：

第一，不同视角可以互相补充。某个视角看不清，另一个视角可能更稳定。
第二，每个视角都能通过深度反投影得到一个三维候选点，多个候选点可以做空间一致性验证。

多视角结果不是简单平均。流程会先过滤掉高度明显不对、深度像素不足、或者落在桌面附近的候选，再把剩下的三维点做聚类。只有落在同一个空间簇里的结果，才会被融合成最终目标。

对于真实视觉模型，我还加了一个保守规则：至少两个视角通过，才允许进入抓取规划。只有一个视角通过时，系统会认为感知不够可靠，而不是冒险执行抓取。

这是机器人系统里很重要的一点：不确定时应该停下来，而不是假装自己知道。

## 不同视觉模型的差异非常明显

在视觉模型上，我先尝试了火山方舟 coding plan 中的 Doubao-Seed-2.0-Pro。它可以接收图片，也能在部分情况下完成识别，但在这个机器人 grounding 任务上并不够稳定。

主要问题是：有时框偏大，有时框到桌面，有时不同视角选到的区域不一致。对于聊天或一般图片理解来说，这些误差可能可以接受；但对于机械臂抓取来说，几厘米的误差就可能导致抓空、碰撞或夹爪压到桌面。

后来我通过 OpenRouter 接入 Gemini 3.5 Flash，效果明显更好。

在同一组高位多视角测试中，Gemini 四个视角全部识别成功，没有视角被几何规则拒绝。它输出的目标框更紧，多视角反投影后的三维位置也高度一致，最后成功完成抓取并抬起方块。

这说明模型能力差异在机器人任务里会被放大。不是所有能“看图说话”的模型，都适合做机器人视觉 grounding。机器人需要的是稳定、精确、可校验的目标定位。

## target_3d 接入抓取规划

有了视觉识别和深度反投影之后，系统可以得到一个三维目标点。但这个点还不能直接当成抓取动作。

对桌面方块来说，深度相机看到的是方块的可见表面，通常接近上表面，而不是方块几何中心。因此在生成抓取姿态前，需要根据方块尺寸做一次转换，估计出方块中心。

然后系统生成三个关键姿态：

方块上方的预抓取姿态。
夹住方块上半部的抓取姿态。
抬升方块的 lift 姿态。

每一段动作都不再是简单插值，而是继续使用 RRT-Connect 规划。也就是说，RRT-Connect 从一个独立的路径规划模块，变成了抓取闭环里的核心运动规划能力。

最终流程变成：

用户给出指令。
机械臂用夹爪根部相机多视角拍照。
视觉模型在图像中找到目标区域。
深度相机把区域变成三维目标点。
多视角几何规则融合目标。
系统生成抓取姿态。
RRT-Connect 规划抓取路径。
MuJoCo 执行动力学抓取。
渲染 GIF，交给人验收。

这是这个阶段最关键的进展：路径规划不再孤立存在，而是被接入了感知、抓取和验证闭环。

## 把机械臂封装成 MCP 工具

在这个阶段，我还把机械臂能力封装成了 MCP 工具。

这样 Codex 不只是能改代码，还能直接调用机械臂能力：让相机拍照、让视觉模型识别、把目标反投影到三维、规划抓取路径、执行仿真抓取，并生成 GIF。

这个封装的意义很大。它把机械臂从“一个仿真程序”变成了“一个可被大模型调用的工具系统”。

但这里也有一个边界：模型本身不能直接等同于 MCP 客户端。比如某个 coding plan 里能选择 Kimi、Doubao 或 Gemini，并不意味着这个模型自己能连接本地机械臂。真正能连接 MCP 的，是承载模型的应用、IDE、agent harness 或 MCP host。

所以后续如果希望更多模型调用机械臂，我更倾向于做一个本地执行器。外部模型只负责提出工具调用意图，本地执行器负责调用机械臂工具，并控制权限、日志、超时和验收边界。

这对未来接真实机械臂尤其重要。模型可以参与决策，但不能裸控机器人。

## 验证：脚本通过不等于任务通过

机器人任务不能只看脚本输出。

很多问题必须通过视觉验收：夹爪有没有穿桌面？方块是不是被真实夹住？动作有没有明显过冲？视觉模型是不是框到了正确目标？多视角是否真的选中了同一个物体？

所以我把验证分成两层：

自动预检：脚本、数值检查和文件检查通过。
人工验收：用户查看每个场景对应的 GIF，确认动作是否真的合理。

这也是为什么每个关键验证案例都需要生成 GIF。对机器人来说，“能跑完”只是第一步，“看起来真的对”同样重要。

## 当前还没解决的问题

第一，多物体歧义还没有解决。现在是单个红色方块场景。下一步需要测试多个同形状、同颜色、不同位置的方块。这个时候，不能再让视觉模型只输出一个目标框，而应该让它输出所有候选，再由几何模块和任务逻辑选择目标。

第二，bbox 不是最终答案。框选区域内部可能包含桌面、阴影、夹爪或背景。对抓取来说，mask 通常会比 bbox 更可靠，后续应该支持基于 mask 的深度提取。

第三，外部模型调用机械臂还需要工程化。Codex 当前已经能调用 MCP，但其他模型要调用机械臂，需要 MCP host 或本地 agent harness，而不是只配置一个模型 API。

第四，目前仍然是仿真抓取。虽然已经加入了接触、摩擦、质量、惯量和执行器控制，但如果未来接真实机械臂，还需要更严格的安全边界、执行确认、急停逻辑和传感器标定。

## 下一步：从单物体抓取走向场景级操作

RRT-Connect 之后，这个项目已经完成了一次关键转变：机械臂不再只是“规划一条路”，而是开始具备“看见目标、理解指令、生成抓取、执行验证”的闭环能力。

下一步，我更关注多物体场景。

比如：桌面上有多个同形状、同颜色的方块，只是位置不同。用户说“抓左边那个”“抓离机械臂最近的那个”“抓上一次没有抓过的那个”，系统应该怎样理解？

我认为比较稳的方向是：

让视觉模型先找出所有候选物体。
让深度相机把每个候选变成三维位置。
用几何关系判断“左边、右边、最近、最远”。
用多视角聚类检查不同视角是否指向同一个物体。
建立场景记忆，给物体分配稳定的身份。

再往后，才是真正的 VLA 方向：视觉感知、语言指令、场景记忆、动作规划、夹爪接触和任务级技能组合。

从这个角度看，RRT-Connect 是运动规划骨架；夹爪、D435i、视觉模型、MCP 和多视角抓取，则是在这个骨架上逐步长出的感知与操作能力。

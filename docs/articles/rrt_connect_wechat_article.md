# 我用 Python 给六轴机械臂继续写运动规划：从 RRT-Connect 到避障和可视化验收

上一篇文章里，我把 Dobot CR5 六轴机械臂的 MuJoCo 简化模型、正运动学、雅可比矩阵和阻尼最小二乘 IK 跑通了。

那一阶段解决的是一个基础问题：

> 给定一个目标位姿，机械臂能不能算出一组关节角，并在 MuJoCo 里到达那里？

这篇继续往下走。现在问题变成：

> 已经知道 A 点和 B 点分别怎么到达，那机械臂应该怎样从 A 运动到 B？

这就不再只是 IK 问题，而是运动规划问题。

---

## 1. 从“能到达”到“能安全地到达”

上一篇里，机械臂已经可以在两个目标小球之间往返。红球和蓝球给的是球心坐标，程序会根据小球半径和工具末端半径，自动把 `tool0` 的目标位置偏移到相切位置。

也就是说，目标不是让工具中心去到小球中心，而是让末端圆头和小球表面相切。

这个语义在这一篇里继续保留。

但仅仅能到达 A 点和 B 点还不够。真实路径还要满足更多约束：

```text
关节不能超限
机械臂不能撞障碍物
机械臂不能穿过地面
路径中间不能穿过目标小球
不能靠近明显奇异的构型
最终轨迹速度和加速度要合理
```

如果只是把 A 点关节角和 B 点关节角做线性插值，路径很可能会从障碍物里穿过去，或者从目标球中间穿过去。视觉上更糟糕的是，它可能穿过地面，或者经过一个腕部突然翻转的构型。

所以这一阶段要做的事，是把“能到达目标”升级成“能安全、合理地到达目标”。

---

## 2. 为什么用 RRT-Connect

机械臂是 6 轴的。规划空间不是三维的 `x, y, z`，而是六维关节空间：

```text
q = [q1, q2, q3, q4, q5, q6]
```

在这个空间里做规划，直接枚举搜索几乎不可行。比如每个关节只粗略分成 100 个取值，六个关节就是：

```text
100^6 = 1,000,000,000,000
```

这还只是非常粗糙的分辨率。

RRT-Connect 不是枚举整个关节空间，而是在关节空间中随机采样。它每次采样一个关节状态 `q_rand`，然后找到当前树里离它最近的节点 `q_near`，沿着 `q_near -> q_rand` 的方向扩展一小步。

这里要注意：这个方向不一定就是“最终目标点方向”。如果 `q_rand` 是随机采样出来的，那么树就是朝随机采样点方向扩展；如果这一次采样使用了 goal bias，把 `q_rand` 直接设成 `q_goal`，那这一轮才是朝最终目标方向扩展。

也就是说，它不是一格一格扫过去，而是不断在空间里“试探”。

普通 RRT 是从起点长一棵树。RRT-Connect 同时维护两棵树：

```text
一棵树从起点 q_start 出发
一棵树从终点 q_goal 出发
```

流程大致是：

```text
随机采样一个 q_rand
起点树朝 q_rand 扩展一步，得到 q_new
终点树从自己的最近节点开始，尽可能朝 q_new 连过去
如果两棵树连上，就得到一条路径
```

这里有两个方向性。

第一个方向性是局部扩展方向：

```text
direction = q_rand - q_near
```

树不是随便长，而是朝当前采样点方向长。这个采样点有时是随机状态，有时会被有意设置成目标状态。

第二个方向性是双向贪心连接。一棵树长出新节点后，另一棵树会主动朝这个新节点靠近，而不是继续完全随机游走。

所以 RRT-Connect 更准确的描述是：

> 随机采样驱动的双向增量搜索。

它不是枚举搜索，也不是全局最优搜索。它的优点是高维空间里很实用，实现也相对直接。缺点是路径质量不一定好，可能比较折，需要后续做 shortcut 和轨迹平滑。

## 3. RRT-Connect 真正依赖的是什么

RRT-Connect 本身并不知道什么是机械臂，什么是障碍物，什么是地面。

它真正依赖的是一个判断函数：

```text
state_valid(q)
```

这个函数回答一个问题：

> 当前这个关节状态 q 能不能用？

在这个项目里，一个状态有效，至少要满足：

```text
关节限位有效
没有碰撞
没有靠近奇异区域
```

所以当前的状态有效性可以写成：

```text
state_valid(q) =
    joint_limits_ok(q)
    and collision_free(q)
    and singularity_margin_ok(q)
```

每次 RRT-Connect 扩展时，不只检查新节点，还会检查两点之间的边。也就是在 `q_near -> q_new` 中间采样多个状态，确保整条边都是有效的。

这一步很重要。否则只检查端点，路径中间可能已经穿过障碍物。

## 4. 碰撞模型：显示用几何不等于规划用几何

MuJoCo 里的模型一开始主要用于显示。显示几何要好看、直观，但它不一定适合做规划碰撞。

比如：

```text
有些显示几何可能互相重叠
有些几何只是为了外观
有些连杆显示得比较细
有些碰撞边界需要更保守
```

所以这一阶段做了一个专门的规划碰撞模型。

思路是：

```text
显示几何：只负责看起来像机械臂
碰撞几何：负责规划时判断会不会撞
```

规划碰撞模型里启用了几类对象：

```text
机械臂各连杆的简化碰撞体
地面
目标小球
额外障碍物
```

这一步把规划器看到的世界补全了。它不再只知道机械臂本体，还知道环境里有什么东西不能碰。

---

## 5. 目标小球也要作为障碍

这是这一阶段一个很重要的修正。

一开始，红球和蓝球只是视觉标记。它们帮助我们看目标在哪里，但规划时会被忽略。

这样会产生一个问题：路径中间可能从小球内部穿过去。

这在视觉上显然不对。因为小球如果代表真实目标、工件或者接触对象，它就不是空气，机械臂路径不能随便穿过它。

现在的规则改成：

```text
目标小球参与碰撞
路径中间不能穿过小球
端点允许工具与小球相切
```

这里有一个细节：端点处本来就是相切接触。MuJoCo 在浮点计算中可能报告一个非常小的负距离，比如亚微米级。这个不是实际穿透，而是数值误差。

所以端点接触允许一个很小的容差：

```text
1e-6 m
```

这个规则更符合任务语义：

```text
相切可以
穿透不行
```

启用小球碰撞后，一些路径会变长，因为规划器现在必须绕开目标球，而不是从球里穿过去。

---

## 6. 地面也要和视觉地面对齐

另一个问题来自 GIF 验收。

有一次自动检查通过，但 GIF 里能看到机械臂和地面发生穿刺。

这说明什么？

说明碰撞模型和视觉模型没有对齐。

当时视觉地面在：

```text
z = 0
```

但碰撞地面在：

```text
z = -0.14
```

所以碰撞检查认为还没碰地，但视觉上已经穿过去了。

修正方式是：

```text
把 floor_collision 提到 z = 0
让碰撞地面和视觉地面对齐
同时加粗部分机械臂 collision capsule
```

这个问题也提醒我：运动规划里的“碰撞正确”不能只看程序输出，还要看渲染结果。可视化不是装饰，它是发现模型语义错误的重要手段。

---

## 7. 障碍物绕行

有了碰撞检查后，就可以给环境加入障碍物。

当前已经做了几类障碍绕行测例：

```text
单箱体阻挡近距离运动
长距离运动中的高箱体
左右跨越时的扫掠区障碍
双箱体形成局部窄通道
```

这里不只是看末端有没有绕开障碍，而是看整条机械臂有没有避开障碍。

例如左右跨越场景里，障碍物并不一定挡在两个目标球心的连线上。它可能挡在大臂、肘部或腕部扫过的区域。

这也是机械臂避障和移动机器人避障很不一样的地方：

> 机械臂要考虑的是整条运动链的空间扫掠，而不是只看末端点。

## 8. RRT 找到的路径还不够好

RRT-Connect 的目标是快速找到一条可行路径，不是找到一条最好看的路径。

所以它找到的原始路径通常比较折，有时会有很多多余的中间点。

因此规划成功后，还要做 shortcut。

shortcut 的思想很简单：

```text
从路径上随机选两个点
尝试直接连接
如果这条直连边有效
就删除中间那一段绕路
重复多次
```

注意，shortcut 不是简单删点。每次删之前仍然要检查：

```text
不碰撞
不穿过小球
不穿地面
不靠近奇异
```

也就是说，shortcut 后的路径仍然必须满足和 RRT 原始路径一样的约束。

障碍物 GIF 默认渲染 shortcut 后的路径。raw RRT 路径保留用于调试，但不作为主要验收动画。

## 9. 还要避开奇异点

RRT-Connect 在关节空间里采样，它天然不会知道机械臂是否接近奇异点。

如果只检查碰撞，可能得到一条“几何上没撞”的路径，但路径经过了 Jacobian 条件数很差的区域。执行时可能出现：

```text
关节速度被放大
末端速度不稳定
腕部突然翻转
控制变得敏感
```

所以这一阶段加入了 Jacobian 奇异性裕度检查。

当前检查三个指标：

```text
condition_number
min_singular_value
manipulability
```

当前阈值是：

```text
max_condition_number = 1000
min_singular_value   = 1e-3
min_manipulability   = 5e-4
```

如果某个关节状态太靠近奇异区域，就会被视为无效状态。这样 RRT-Connect 在搜索时就会主动绕开这些区域。

---

## 10. 一个典型问题：左右跨越时的 IK 分支

左右跨越测例暴露了一个很典型的问题。

同一个末端目标位姿，可能有多组 IK 解。比如肘上、肘下，或者腕部不同旋转分支。

一开始，左右跨越的两个端点本身都有效，但 A 到 B 的路径会穿过一个接近奇异的区域。扫描后发现，某些路径上的 Jacobian 条件数会飙到几千。

这不是 RRT-Connect 算法本身的问题，而是 IK 分支组合不好。

解决方式是：

```text
枚举多个 IK 候选
计算每个候选的奇异性指标
比较不同 A/B 组合之间的路径质量
选择更健康的一组 IK seed
```

调整后，同样是左右跨越任务，路径最差条件数降到了几十量级。

这件事很有启发：

> 对机械臂来说，IK 分支选择本身就是规划的一部分。

如果端点 IK 解选得不好，后面的路径搜索会非常困难；如果端点构型选得合理，规划会顺很多。

## 11. 从路径到轨迹

RRT-Connect 和 shortcut 得到的是几何路径，也就是一串关节角：

```text
q0, q1, q2, ...
```

但真正播放或执行时，需要的是带时间的轨迹：

```text
q(t)
dq(t)
ddq(t)
```

当前做了一个关节空间时间参数化，让每段运动满足速度和加速度约束：

```text
max_joint_velocity     = 0.8 rad/s
max_joint_acceleration = 1.6 rad/s^2
```

轨迹生成后，还会重新采样验证：

```text
速度是否超限
加速度是否超限
采样状态是否碰撞
采样状态是否靠近奇异
```

这一步的意义是：规划路径本身可行，不代表按时间播放后就一定安全。轨迹层还要再检查一次。

---

## 12. 为什么一定要看 GIF

自动测试能检查很多东西：

```text
模型能不能加载
IK 是否成功
路径是否碰撞
路径是否远离奇异
轨迹速度和加速度是否合理
GIF 文件是否有效
```

但它不能完全替代人的视觉判断。

比如：

```text
动作是否明显别扭
有没有视觉穿模
绕障是否符合直觉
末端是否真的在目标点停留
姿态是否看起来正确
```

所以当前验收分两层：

```text
automatic pre-check passed
user GIF confirmation
```

也就是说，脚本通过只代表自动预检通过，最终还需要人看 GIF。

为了让 GIF 更适合验收，现在做了两个调整：

```text
分辨率提升到 960 x 720
到达 A/B 目标点后默认停留约 1 秒
```

停留这一秒很重要。否则机械臂刚到目标点就离开，很难判断末端姿态和接触关系。

## 15. 还有哪些要完善

当前这套系统已经形成闭环，但还不是工业级规划器。

后面还要继续做几件事。

### 15.1 更精确的碰撞几何

当前碰撞几何主要是简化的 capsule、cylinder 和 box。它已经能用于规划验证，但还不是精确 CAD 碰撞模型。

后续可以继续区分：

```text
显示几何
规划碰撞几何
安全膨胀几何
```

### 15.2 更多障碍类型

当前障碍主要是 box。后面可以增加：

```text
cylinder
sphere
mesh obstacle
桌面
夹具
墙面
低净空
更窄通道
```

### 15.3 无解场景

现在主要验证“能找到路径”。但真实系统还需要知道什么时候无解：

```text
目标不可达
端点本身碰撞
障碍完全封死
所有 IK 分支都不可用
```

### 15.4 更高质量的路径优化

RRT-Connect 擅长找可行路径，但不保证路径最短、最平滑。

后续可以加入：

```text
更强的 shortcut
曲线平滑
clearance 优化
manipulability 优化
路径长度代价
```

### 15.5 轨迹导出和真实执行

当前主要面向 MuJoCo 和 GIF 验收。后续如果接真实控制器，需要导出：

```text
时间戳
关节位置
关节速度
关节加速度
执行状态
失败原因
```

### 15.6 更严格的自碰撞检查

当前简化模型仍然存在一些结构性重叠，所以自碰撞检查还没有完全打开。后面需要更精细的 collision geometry，才能稳定启用严格自碰撞。

## 16. 小结

上一篇解决的是：

```text
机械臂模型是否可信
FK / Jacobian / IK 是否正确
末端能不能按姿态接触目标球
```

这一篇解决的是：

```text
从 A 到 B 的路径是否可信
是否能避开地面、障碍和目标小球
是否远离奇异区域
是否满足速度和加速度限制
是否能通过 GIF 做人工验收
```

RRT-Connect 只是其中一个模块。真正重要的是把“状态是否有效”定义清楚：

```text
关节限位有效
碰撞有效
小球避障有效
地面避障有效
奇异性裕度有效
轨迹采样有效
```

有了这个定义，RRT-Connect、shortcut、轨迹时间参数化和 GIF 验收才组成了一个完整闭环。

当前阶段的状态可以总结为：

```text
automatic pre-check passed;
waiting for user GIF confirmation.
```

也就是说，自动预检已经证明当前规则下模型、规划、碰撞、奇异性和轨迹采样都能通过。最后是否真正通过，还要继续看每个 GIF 的人工确认结果。

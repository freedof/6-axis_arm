# 六轴机械臂怎么绕开障碍走过去？浅谈 RRT-Connect 与运动规划

上一篇里，我把越疆 Dobot CR5 的 MuJoCo 简化模型、正运动学、雅可比和阻尼最小二乘 IK 跑通了，机械臂已经能算出"到达某个目标位姿要怎么摆关节"。

但能算出终点，不等于知道怎么走过去。这一篇要回答的是下一个问题：

> 已经知道 A 点和 B 点各自怎么到达，机械臂应该**沿什么路径**从 A 运动到 B？

这就不再是逆运动学问题，而是**运动规划**问题了。

先看一个效果——机械臂要在两个目标球之间往返，但中间被一个高箱子挡住，规划器自动绕了过去：

![长距离往返中绕开高箱体](<F:\6-axis arm\outputs\obstacle_scene\tc_rrt_obstacle_002_compressed.gif>)

下面按思路、机理、示例到下一步，逐层展开。

---

## 一、思路：从"能到达"到"能安全地到达"

上一篇结束时，机械臂已经能在红蓝两球之间往返：球心坐标加上小球半径和工具半径，程序会自动把末端偏移到"圆头和球面相切"的位置。这个语义这一篇继续保留。

但**只把 A、B 两点的关节角做线性插值是不够的**。直线插值出来的路径很可能从障碍物里穿过去、从目标球中间穿过去，甚至扎进地面，或者中途经过一个腕部突然翻转的别扭构型。

所以这一阶段的目标，是把"能到达目标"升级成"能安全、合理地到达目标"。一条真正可用的路径要同时满足：关节不超限、不撞障碍、不穿地面、不穿目标球、不靠近奇异构型，最终的速度和加速度也要合理。

把这些约束讲清楚、并让规划器自动满足它们，就是这篇的全部内容。

---

## 二、为什么选 RRT-Connect

机械臂是六轴的，规划的空间不是我们熟悉的三维 `(x, y, z)`，而是六个关节角组成的六维空间 `q = [q1, …, q6]`——每一个 `q` 对应机械臂的一种姿态。问题就是在这个六维空间里，从起点姿态 `q_start` 找一条不撞东西的路连到终点姿态 `q_goal`。

最直接的想法是把空间切成网格逐个试，但这条路走不通：哪怕每个关节只粗分成 100 档，六个关节的组合也有 `100⁶ = 10¹²`（一万亿）种，而 100 档还是非常粗的分辨率，根本算不过来。

RRT-Connect 换了个思路——**不遍历整个空间，而是随机撒点、一点点试探着长出一条路**。它的基本动作只有三步，不断重复：

```text
1. 随机采样一个姿态 q_rand
2. 在已经探出来的节点里，找离它最近的那个 q_near
3. 从 q_near 朝 q_rand 迈一小步，得到新姿态 q_new
   （这一步要检查：q_new 以及沿途有没有撞到东西，合法才保留）
```

这样不断重复，合法的节点就像树枝一样从起点慢慢生长、铺满可行区域，直到够到终点。

RRT-Connect 比普通 RRT 更快的关键，在于"双向"二字。普通 RRT 只从起点长一棵树，碰运气撞上终点；RRT-Connect 同时从起点和终点各长一棵树，每一轮一棵树新长出一个节点后，**另一棵树就立刻朝这个新节点贪心地靠过去**，两棵树相向生长、主动会合，一旦接上就拼成一条完整路径。

一句话概括，它是**靠随机采样驱动、两棵树相向逼近的增量搜索**。好处是在高维空间里特别实用、实现也不复杂；代价是它只求"快速找到一条能走的路"，不保证这条路最短最好看——原始路径往往比较折，需要后面再做平滑（这一步放到第四节讲）。

## 三、机理：规划器真正依赖的是"状态是否有效"

这里有个容易被忽略的关键：**RRT-Connect 本身根本不知道什么是机械臂、什么是障碍物、什么是地面**。它唯一依赖的，是一个判断函数：

> 给我一个关节状态 `q`，告诉我它能不能用？

整套规划能力强不强，几乎全取决于这个 `state_valid(q)` 定义得够不够完整。在这个项目里，一个有效状态至少要同时满足三件事：

```python
state_valid(q) = joint_limits_ok(q)      # 关节在限位内
             and collision_free(q)         # 不发生碰撞
             and singularity_margin_ok(q)  # 不靠近奇异区域
```

而且每次扩展时不能只检查端点，还要在 `q_near → q_new` 这条边中间多采样几个点逐一检查，否则端点都合法、中间却可能已经穿过障碍。下面把这三件事拆开讲，它们正是这一阶段踩过的几个坑。

### 3.1 显示用几何 ≠ 规划用几何

MuJoCo 里最初的模型是给人看的：要直观、好看。但显示几何不一定适合做碰撞判断——有些是纯为外观、有些互相重叠、有些连杆画得偏细，碰撞边界则需要更保守。

所以这一阶段专门做了一套**规划碰撞模型**，和显示模型分家：显示几何只负责"看起来像机械臂"，碰撞几何只负责"判断会不会撞"。规划模型里启用了各连杆的简化碰撞体、地面、目标小球和额外障碍物——这一步把规划器眼里的世界补全了。

### 3.2 目标小球也要算作障碍

一开始红蓝两球只是视觉标记，规划时被忽略。结果路径会从小球内部穿过去——如果小球代表真实工件或接触对象，它就不是空气，路径不能随便穿过。

现在的规则改成：小球参与碰撞，路径中途不能穿过它，但**端点允许工具和小球相切**。这里有个数值细节：端点本就是相切接触，MuJoCo 浮点计算可能报告一个微米级的负距离，那不是真穿透而是数值误差，所以端点接触留了 `1e-6 m` 的容差。一句话——相切可以，穿透不行。启用小球碰撞后，部分路径会变长，因为规划器现在必须绕开球而不是钻过去。

### 3.3 碰撞地面要和视觉地面对齐

有一次自动检查通过了，GIF 里却能看到机械臂扎进地面。原因是碰撞模型和视觉模型没对齐：视觉地面在 `z = 0`，碰撞地面却在 `z = -0.14`，于是碰撞检查以为还没碰地，画面上早就穿过去了。修正办法是把碰撞地面提到 `z = 0` 和视觉对齐，同时把部分连杆的碰撞胶囊加粗一点。

这件事的教训是：**运动规划里的"碰撞正确"不能只看程序输出，还得看渲染结果**。可视化不是装饰，它是发现模型语义错误的重要手段。

### 3.4 还要避开奇异点

先说什么是奇异点。机械臂在某些特殊姿态下——比如手臂完全伸直、或某两个关节轴恰好共线——会突然"丧失"沿某个方向运动的能力：末端想往那个方向只挪一点点，几个关节却要疯狂大幅转动才能凑出来。用上一篇的雅可比来说，就是这个矩阵在这些姿态下"退化"了（条件数极大、接近不可逆），关节速度和末端速度之间的映射变得极不稳定。这类姿态就叫奇异位形（singularity）。

RRT-Connect 在关节空间里随机采样，天然不知道机械臂是不是正接近奇异。如果只查碰撞，很可能得到一条"几何上确实没撞"、却从奇异区域穿过去的路径，真到执行时就会出问题：关节速度被放大、末端速度不稳、腕部突然翻转、控制变得异常敏感。

所以这一阶段把雅可比的奇异性裕度也纳入 `state_valid`，监控条件数、最小奇异值和可操作度三个指标，太靠近奇异区域的状态直接判为无效，规划器搜索时就会主动绕开。

## 四、示例：让整条手臂都绕开障碍

有了完整的 `state_valid`，就能往环境里塞障碍物看规划器怎么反应。这里要强调一点，机械臂避障和移动机器人避障很不一样：

> 移动机器人基本只看一个点会不会撞；机械臂要考虑的是**整条运动链扫过的空间**。

障碍未必挡在两个目标球心的连线上，它可能正好卡在大臂、肘部或腕部扫掠的区域里。下面几个测例就是按这个思路设计的。

**单箱体阻挡近距离接触**——最基础的绕行：

![单箱体阻挡下的近距离接触绕行](<F:\6-axis arm\outputs\obstacle_scene\tc_rrt_obstacle_001_compressed.gif>)

**左右跨越时的扫掠区障碍**——箱子不在末端直线上，而挡在手臂横扫的路径中：

![左右跨越中绕开扫掠区障碍](<F:\6-axis arm\outputs\obstacle_scene\tc_rrt_obstacle_003_compressed.gif>)

**双箱体形成的窄通道**——规划器要在两箱之间找一条窄缝穿过：

![双箱体窄通道绕行](<F:\6-axis arm\outputs\obstacle_scene\tc_rrt_obstacle_004_compressed.gif>)

作为对照，下面是没有箱子、但需要左右大幅跨越并切换末端姿态的规划路径，可以看出即便无障碍，规划出来的也是一条平滑合理的轨迹，而不是生硬的关节直线插值：

![左右跨越水平接触的规划路径](<F:\6-axis arm\outputs\roundtrip_planned_tc_rrt_multi_005_compressed.gif>)

### 路径找到了，还要再打磨

RRT-Connect 的目标是**快**地找到一条可行路径，不是找最好看的路径，所以原始路径往往很折、带很多多余拐点。规划成功后会再做一遍 shortcut：在路径上随机取两点尝试直连，若这条直连边合法就删掉中间那段绕路，反复多次。注意 shortcut 不是简单删点——每次直连仍要通过和原路径一样的全部检查（不碰撞、不穿球、不穿地、不靠近奇异）。上面的避障动画默认渲染的都是 shortcut 之后的路径。

### 从几何路径到带时间的轨迹

shortcut 之后得到的还只是一串关节角 `q0, q1, q2, …`，是几何路径，不能直接执行。真正播放需要带时间的轨迹 `q(t), dq(t), ddq(t)`。所以最后做一次关节空间时间参数化，让每段运动满足速度上限 `0.8 rad/s`、加速度上限 `1.6 rad/s²`，生成后再重新采样验证一遍——路径本身可行，不代表按时间播放后一定安全，轨迹层要再兜一次底。

### 一个有意思的发现：选 IK 分支也是规划的一部分

左右跨越测例暴露过一个典型问题：同一个末端目标位姿有多组 IK 解（肘上、肘下、腕部不同旋转分支）。两个端点单看都合法，但某些端点组合之间的路径会穿过接近奇异的区域，条件数飙到几千。这不是 RRT-Connect 的锅，而是端点 IK 分支没选好。办法是枚举多个 IK 候选、算各自的奇异性指标、比较不同 A/B 组合的路径质量，挑一组更"健康"的 seed——调整后同样的任务，路径最差条件数从几千降到了几十。

> 对机械臂来说，IK 分支的选择本身就是规划的一部分。端点构型选得好，后面的路径搜索会顺很多。

## 五、下一步：从"能规划"走向"会看、会想、会动手"

这一阶段已经形成一个闭环：规划碰撞模型、显示与碰撞几何分离、地面和目标小球都作为正式障碍、MuJoCo 支撑的碰撞检查、关节空间 RRT-Connect、shortcut 简化、奇异性裕度检查、轨迹时间参数化，再加上一批基础测例和障碍绕行测例。项目从上一篇的"能到达目标"，推进到了这一篇的"能在约束下规划到目标"。

短期内，它离工业级规划器还有距离，有一批工程上的事要补：把碰撞几何做得更精确（进一步区分显示几何、规划几何、安全膨胀几何，并稳定启用严格的自碰撞检查）；支持更多障碍类型（圆柱、球、mesh、桌面、夹具、墙面、低净空、更窄的通道）；明确识别**无解场景**（目标不可达、端点本身碰撞、障碍完全封死、所有 IK 分支都不可用）；引入更高质量的路径优化（更强的 shortcut、曲线平滑、间隙与可操作度优化）；以及把轨迹导出对接真实控制器，输出时间戳、关节位置/速度/加速度和执行状态。

不过比起这些渐进式的打磨，我更想推进的是另一个方向：**让大模型来操作这台虚拟机械臂**。现在的流程还是人来指定 A、B 目标点，规划器只负责"怎么走过去"；而真正想做的，是给场景加入深度相机，让机械臂能感知三维环境，再由大模型理解"要干什么"、自动拆解成一连串目标和约束，交给底层的 IK 和 RRT-Connect 去执行。要让它真正"动手"，末端也得从现在这个只用来接触的圆头，换成夹爪或其他执行器（吸盘、电批等），并把抓取、夹持、释放这些动作也纳入规划。沿着这条路往下，自然会走到 **VLA（Vision-Language-Action）** ——把视觉感知、语言指令和动作输出端到端地连起来：人说一句话，机械臂自己看懂场景、想清楚步骤、规划并完成动作。这一篇打好的运动学和运动规划底座，正是为后面这套"感知—理解—规划—执行"的闭环做准备。

## 小结

如果说上一篇解决的是"机械臂模型可不可信、FK/雅可比/IK 对不对、末端能不能按姿态接触目标球"，那这一篇解决的就是"从 A 到 B 的路径可不可信、能不能避开地面/障碍/目标球、是否远离奇异、是否满足速度和加速度限制"。

RRT-Connect 只是其中一个模块。真正决定成败的，是把"状态是否有效"定义清楚——关节限位、碰撞、小球避障、地面避障、奇异性裕度、轨迹采样，每一条都到位之后，RRT-Connect、shortcut、时间参数化和可视化验收才真正组成一个完整闭环。

而再往后，真正想做的不只是把这套规划器打磨得更工业级，而是给它装上"眼睛"和"大脑"：加入深度相机做三维感知，让大模型来理解任务、自动拆解目标，末端换成夹爪去真正抓取操作，一步步走向 VLA 那种"人说一句话、机械臂自己看懂并完成"的闭环。这一篇打好的运动学和运动规划底座，正是为后面这条路做准备。
